# Plan 043: WebUI integration

## Goals & Success Criteria
- Enable Viro scripts to spin up and control a native WebUI window (HTML/CSS/JS surface) while the interpreter continues running in the same CLI process.
- Provide an idiomatic API (natives/dialect words) that lets scripts create windows, inject markup, send data, and register event callbacks without breaking existing programs or requiring a new CLI mode.
- Integrate the go-webui bindings (`github.com/webui-dev/go-webui`) through a dedicated runtime layer that manages WebUI lifecycle, threading, and GC interactions.
- Support future hot-reload workflows by keeping window state and asset re-rendering abstractions extensible (no bundling yet, but plan for refreshing HTML and handlers efficiently).
- Align naming with Viro conventions by exposing all WebUI capabilities as dot-access methods on the shared `webui` object (e.g., `webui.window`).
- Maintain normal Viro guidelines: specs + contract tests precede runtime work, `viro-coder`/`viro-reviewer` handle edits, and `help` / docs describe the new API.

## Architecture Overview
- **Runtime service**: Introduce `internal/webui` (new package) encapsulating go-webui usage (window creation, event loop, cleanup). This package exposes a `Manager` that creates windows, tracks handles, and marshals events through channels understood by the evaluator.
- **Value representation**: Introduce a dedicated `webui-window!` value implemented as `value.WebUIWindow` in `internal/value`. Provide `value.NewWebUIWindow(id uint32)` constructor plus helpers `value.IsWebUIWindow(v value.Value) bool` and `value.MustWebUIWindow(string, v value.Value) *value.WebUIWindow` so natives can enforce type safety. The struct only stores the numeric handle ID; actual `*webui.Window` instances stay inside the manager maps, preventing direct user access while keeping handles comparable and GC-friendly.
- **Event dispatch**: go-webui callbacks run on their own goroutines. `internal/webui.Manager` captures `webui.on` registrations as `HandlerEntry{WindowID, Event, Selector, HandlerBlock value.Block, CapturedFrame frame.Index}` and pushes immutable `EventMessage{HandlerEntry, Payload value.Value, Timestamp}` structs onto a queue (`Manager.Events() <-chan EventMessage`). The evaluator (likely via `internal/eval` or a helper in `internal/native`) drains that channel when scripts call `webui.poll window`: it creates a child frame whose parent is the stored `CapturedFrame`, binds handler args `event-name`, `event-selector`, `event-payload`, and `event-window` inside that frame (using the message contents), executes the handler block via standard evaluators, and propagates script errors/break signals back to the caller so `webui.poll` can bubble failures.
- **Hot reload hook**: Rather than bundling assets, the API allows scripts to update markup (`webui.render window html`) and optionally register a file watcher (in future). In this phase we expose `webui.refresh window block-of-fn` hooks so that editors or user scripts can implement reload loops.

- **Lifecycle integration**: CLI remains unchanged; `cmd/viro/main.go` already drives evaluation. When a script exits, the manager closes any remaining windows. Conversely, closing the last WebUI window closes the manager’s `Done() <-chan struct{}` so the evaluator can detect shutdown without racing on goroutines and bail out gracefully if the script was waiting on events.

## Proposed Viro API Surface
All WebUI entry points hang off the shared `webui` object and must be referenced via dot notation (`webui.window`, `webui.render`, etc.) to align with Viro naming conventions.
- **`webui.start`** — initializes the WebUI subsystem (idempotent). Returns a context map with defaults (window size, title). Usually auto-called by other `webui.*` natives.
- **`webui.window spec-block`** — creates or reuses a window. `spec-block` accepts keys `title text!`, `width integer!`, `height integer!`, `debug? logic!`, `resizable? logic!`, `icon file!`, `source file!|url!`, and `html string!|binary!`. Missing keys fall back to manager defaults from `webui.start`. Returns a `webui-window!` handle; `source` is resolved exactly like the `source` option to `webui.render` (file path tracked for watcher loops, bytes read once and cached for diagnostics) before the initial render occurs, while `html` in the spec is treated like calling `webui.render` immediately after creation.
- **`webui.render window markup options?`** — replaces the current DOM with the provided markup. `markup` accepts `string!`, `binary!`, or `file!` (file contents read once per call; binary payloads are streamed as-is, whereas strings are UTF-8 encoded). Options block keys: `base-path file!` (resolves relative URLs), `source file!` (path tracked for hot reload loops and reused by `webui.window` when specified there), `data map!/object!/block!` (JSON-encoded and assigned to `window.viroscope` before render), and `content-type word!`. `content-type` only accepts the enumerated words ``text/html``, ``text/plain``, ``application/xhtml+xml``, ``application/json``, or ``text/javascript``; invalid words raise a spec error, and binary markup requires callers to supply one of those words so the browser interprets the bytes correctly. `webui.render` always resets the page and replays registered handlers, unlike `webui.inject`, which simply evaluates the snippet in the existing DOM without clearing state, so all hot-reload guidance references `webui.render` (with `webui.window` merely seeding the first call using the same option semantics).
- **`webui.send window message payload`** — pushes data to the JS side (maps to go-webui `Window.Send()`). `message` must be `text!` naming the channel; `payload` accepts `none`, `logic!`, `integer!`, `decimal!`, `string!`, `binary!`, `map!`, `block!`, or `object!`. Non-string types are serialized via the existing `value.ToJSON` helper so JS receives canonical JSON (binary encoded as base64). Strings/binaries are passed through untouched. Errors bubble if serialization fails.
- **`webui.on window event selector handler-block`** — registers a callback invoked when the browser emits `event`. `event` must be `text!`; `selector` accepts `text!` (CSS selector/id) or `block!` of strings. At registration time the runtime captures `handler-block` plus the current frame index for lexical bindings. When an event fires, the payload posted to the queue is normalized into a map with keys `name text!`, `selector text!`, `data any-value!`, `window webui-window!`, and `raw string!` (original JSON). `data` (`event-payload`) comes from decoding the incoming JSON blob via the same `value.FromJSON` helpers the CLI uses; if decoding fails or the UI sends a non-JSON string, `data` falls back to the raw string/binary while `raw` preserves the exact bytes so handlers can re-parse. Inside `handler-block`, words `event-name`, `event-selector`, `event-payload`, and `event-window` are auto-bound to those values so scripts can destructure without manual arguments.
- **`webui.poll window`** — drains pending events and runs associated handler blocks. It dequeues all messages targeting the supplied window (or every window when `window` is `none`). Each handler executes in a fresh child frame with locals `event-name`, `event-selector`, `event-payload`, and `event-window` plus any user-defined locals captured at registration. Script errors raised inside handlers abort `webui.poll` and propagate to the caller so loops can handle failures deterministically. The function listens to `Manager.Done()` as well—once that channel is closed and the queue is empty, `webui.poll` immediately returns `none` so outer `wait` loops can exit cleanly instead of spinning. Intended for cooperative event loops (e.g., inside `forever [wait 0.1 webui.poll window]`). Later we can add auto-poll.
- **`webui.close window`** — closes the handle and removes event registrations. Returns logic! showing whether a window was actually closed. When the last open window closes, the manager closes its `Done() <-chan struct{}` (rather than sending sentinel values), signalling every waiter exactly once so the evaluator can exit any `wait` loops gracefully and `webui.poll` immediately returns `none` on the next drain.
- **`webui.ready? window`** — returns logic! to let scripts gate rendering. It becomes `true` only after the underlying go-webui window reports its first `Ready` callback (after `webui.render` seeds the DOM) and flips back to `false` if a new full-page `webui.render` begins or the window closes, so loops can wait for readiness without missing intermediate refreshes.
- **Hot reload helpers**: `webui.inject window html` evaluates markup snippets in the existing page context (delegates to go-webui `Run()`), so it is ideal for incremental updates and does not reset event handlers. `webui.render` remains the full-page replacement operation. `webui.inject` accepts `string!|binary!` payloads only; callers that want file-driven updates should read the file then inject. Provide guidance in docs for wiring watchers even though no built-in watcher is added yet.
- All natives should expose documentation via `NativeDoc` so `help webui.window` etc. work. API leaves room for expansions (e.g., `webui.dialog`, `webui.storage`) by keeping naming consistent.

## Implementation Roadmap
1. **Specification + documentation prep**
   - Extend `/specs/002-implement-deferred-features/contracts/` (likely new `webui.md`) summarizing requirements, API signatures, event semantics, and hot-reload considerations.
   - Update `/docs/viro_architecture_knowledge.md` or a new `/docs/webui.md` detailing CGO/platform requirements, lifecycle semantics, and the managed value type so the CLI/docs stay in sync.
2. **Testing scaffolding (TDD)**
   - Add contract tests in `test/contract/webui_test.go` covering handle creation, render invocation (mocked—no real UI), event registration semantics, and error cases (bad spec block, double close). Tests can use dependency injection (mock Manager) or rely on build tags to skip UI if not supported in CI.
   - For pure Go coverage, provide unit tests for the `internal/webui` manager (using stubbed go-webui interfaces) verifying handle lifecycle.
3. **Runtime wrapper package**
   - Create `internal/webui/manager.go` encapsulating go-webui usage: initialize library once, maintain `map[int]*webui.Window`, offer `CreateWindow`, `Render`, `Send`, `Close`, `RegisterEvent` functions, expose `Event` structs (id, payload, handler). Define a `Manager` interface (covering those methods + `Poll`, `CloseAll`, `Done`) so tests can swap implementations.
   - Add a `Queue` struct (channel-based) that stores events and ensures evaluator-driven polling. Provide cleanup on process exit and emit a stub implementation (`manager_stub.go` under `//go:build webui_stub`) that satisfies the interface but never touches CGO, enabling contract/unit tests on headless CI.
4. **Value & native plumbing**
   - Introduce a `webui-window!` value wrapper in `internal/value` (likely similar to `action!` or `native!` wrappers). Provide constructor helpers and type guards used by natives.
   - Implement new natives in `internal/native/webui.go` with registration handled by `internal/native/register_webui.go`. Ensure each native enforces arity/spec validation and interacts with the manager.
   - Hook registration into `internal/native/register.go` (where categories register) so the new natives are always available.
5. **Evaluator integration**
   - Extend `internal/eval/evaluator.go` (or companion) with optional event loop support: when scripts call `webui.poll`, evaluator drains manager queue and executes stored handler blocks via standard evaluation primitives. Provide `wait`-friendly patterns (maybe integrate with `action/wait`?).
   - Ensure interpreter shuts down lingering windows by calling `webui.Manager.CloseAll()` when evaluation completes or upon signal.
6. **CLI + build adjustments**
   - Add `github.com/webui-dev/go-webui` to `go.mod`, ensure CGO requirements documented (WebKitGTK on Linux, Edge WebView2 on Windows, etc.). Provide guard rails for headless CI via `webui_stub` build tag plus `//go:build webui && !webui_stub` for real integrations. No new CLI flags/modes; only optional verbose logging under existing `--verbose`.
   - Document dependency installation steps in `docs/observability.md` or the dedicated `/docs/webui.md`, including `CGO_ENABLED=1` expectations.
7. **Hot-reload considerations**
   - Provide helper functions within `webui.render` to accept `source` parameter referencing a file path; manager reads file contents each call so user-managed watchers can re-invoke it quickly.
   - Outline manual workflow in docs (use `watch` script + `webui.render`). Keep architecture ready for future `webui.watch` native by isolating file IO from window state.
8. **Help & examples**
   - Update `examples/` with a new `10_webui.viro` demonstrating open/render/event loop/hot reload stub.
   - Extend `docs/repl-usage.md` or new doc to explain running scripts that open a window.
9. **Review + polish**
   - Run targeted tests (`go test ./internal/webui ./test/contract -run WebUI`).
   - Follow mandated workflow: implementation via `viro-coder`, review via `viro-reviewer` before merging.

## Testing Strategy
- **Contract tests (`test/contract/webui_test.go`)**: Use the `internal/webui.Manager` interface plus the `webui_stub` build tag implementation to assert script-level semantics (handle creation, errors, event queue ordering) without CGO. When the real manager is unavailable, natives must fall back to deterministic `verror.NewScriptError` branches documented in the spec.
- **Unit tests (`internal/webui/manager_test.go`)**: Validate the real manager handles concurrency (create → render → close), queueing, and cleanup. Provide a stub `testManager` that satisfies the interface by recording calls so logic can be exercised on headless runners, and gate CGO-dependent tests behind `//go:build webui && !webui_stub`.
- **Integration sanity**: Optional manual test script (`examples/10_webui.viro`) demonstrating open → render → event -> close; run via `./viro examples/10_webui.viro` on a workstation with GUI support, and note in docs that it requires CGO + WebKit bindings installed.
- **Manual guidance**: Document steps for verifying hot reload (e.g., run `entr` or `fswatch` to re-run `webui.render` when HTML file changes) until automation exists.

## Risks & Mitigations
- **GUI dependency / CGO availability**: Real WebUI windows may fail on headless runners or builders lacking CGO toolchains. Mitigate with the `Manager` interface, `webui_stub` build tag, and explicit docs covering OS package requirements; gate real integrations behind `//go:build webui && !webui_stub`.
- **Event loop deadlocks**: Handlers running inside go-webui callbacks could race with interpreter state. Mitigate via explicit queue + `webui.poll`, never executing handler blocks on go-webui goroutines.
- **Resource leaks**: Forgetting to close windows could leave goroutines running. Ensure manager tracks handles via `sync.Map`, reference counts, and `CloseAll` invoked on interpreter exit.
- **API churn**: Early API choices might limit future features. Keep naming consistent (`webui.*` namespace), use spec blocks for extensibility, and store metadata in docs to guide future refinements.
- **Hot reload complexity**: Without bundling, users rely on manual watchers. Provide clear guidance and stable `webui.render` semantics so adding watchers later does not break scripts.

## Viro Guidelines Reference
- Follow `AGENTS.md`: specs + contract tests precede runtime work, modifications flow through `viro-coder` and `viro-reviewer` agents, no inline Go comments, use constructor helpers (`value.New*`).
- Natives documented through `NativeDoc` for `help`, tests use table-driven style, and CLI remains unchanged per instruction.
